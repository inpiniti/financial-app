# handle-issue 워크플로우

운영 중 발견된 버그(예: 체결 통보 누락으로 인한 유령 보유 종목 방치), 예외 상황, 기능 개선 요구사항을 **DDD 도메인 중심**으로 체계적으로 해결하는 엔드투엔드 워크플로우입니다.

---

## 1. 워크플로우 핵심 철학

> **"코드를 무작정 고치지 않고, 도메인 불변식과 책임을 먼저 갱신한 후 코드로 투영한다."**

1. 문제가 발생한 비즈니스 영역(도메인)을 명확히 식별합니다.
2. 기존 도메인에 부합하지 않는 새로운 개념이라면 `add-domain`으로 경계를 먼저 정의합니다.
3. 해당 도메인의 문서(`feature.md`, `README.md` 등)에 **새로운 방어 규칙 및 해결 스펙**을 기록합니다.
4. 문서화된 스펙을 기준으로 실제 코드를 수정하고 단위 테스트로 회귀를 방지합니다.

---

## 2. 단계별 실행 절차

### 단계 1: 이슈 분석 및 원인 파악 (Diagnosis)
1. 사용자가 제기한 문제 현상을 구체적으로 분해합니다:
   - 증상 (Symptom): 예) "체결 응답을 못 받아 보유에 계속 남아서 감지 중임"
   - 근본 원인 후보 (Root Cause): 브로커 REST 폴링 누락, 웹소켓 끊김, 체결 상태와 로컬 포지션 상태 간의 불일치 등
   - 위험도 및 영향도: 슬롯 점유 낭비, 이중 발주 위험, 잔고 왜곡

### 단계 2: 관련 도메인 식별 및 매핑 (Domain Identification)
1. `docs/domain/` 하위의 도메인 지도(`docs/domain/README.md`)를 확인합니다:
   - 이 이슈의 책임이 기존 도메인에 속하는가?
     - 예) 주문 누락/체결 응답 $\to$ `docs/domain/주문/`
     - 예) 보유 포지션 잔고 동기화 $\to$ `docs/domain/포지션/`
     - 예) 슬롯 점유 및 타임아웃 $\to$ `docs/domain/오토파일럿/`
2. **기존 도메인이 없는 경우**:
   - `add-domain` 워크플로우를 먼저 호출하여 신규 도메인을 등록합니다.

### 단계 3: 도메인 명세 업데이트 (Spec / Feature Update)
해당 도메인의 문서에 이슈 재발 방지를 위한 규칙을 추가합니다:
- **`feature.md`**: 신규 유스케이스 및 예외 처리 흐름 추가
  - 예: `UC-ORD-04: 체결 불일치 감지 및 잔고 재대조(Reconciliation) 주기적 동기화`
- **`README.md`**: 도메인 불변식(Invariants) 추가
  - 예: *"보유 상태가 N분 이상 지속되거나 틱이 없으면 KIS 실잔고 조회를 통해 유령 포지션을 강제 정리한다."*
- **`architecture.md`** (필요시): 이벤트 흐름 및 예외 복구 시퀀스 다이어그램 갱신

### 단계 4: 코드 구현 및 설계 반영 (Implementation)
도메인 문서에 정의된 규칙에 맞춰 실제 코드를 작성/수정합니다:
1. 도메인 로직/엔티티/어댑터 수정 (예: `orderPortAdapter.ts`, `positionManager.ts`, 잔고 폴백 추가 등)
2. 환경 설정 또는 상수 정의 (예: 타임아웃 시간, 최대 재대조 주기 등)

### 단계 5: 테스트 작성 및 검증 (Verification)
1. 해당 이슈 상황을 재현하는 단위 테스트(`.test.ts`) 작성
   - 모킹된 브로커 응답을 통해 체결 미도착 시 복구 로직 검증
2. `npm test` 또는 `npx vitest run ...` 명령어로 테스트 통과 확인
3. 사이드 이펙트가 없는지 기존 관련 테스트 함께 실행

### 단계 6: 사용자 보고 및 완료 (Wrap-up)
- 어떤 도메인 문서에 어떤 규칙/feature가 추가되었는지 요약
- 코드 수정 내용 및 테스트 통과 결과 보고
