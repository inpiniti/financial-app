# find-domain 워크플로우

현재 프로젝트(`financial-app`)의 코드베이스(`core/`, `features/`, `components/`, `lib/`, `app/`, `supabase/` 등)를 체계적으로 분석하여,
아직 공식 도메인으로 명세화되지 않았거나 분리가 필요한 잠재적 도메인을 발굴하고 사용자 확인을 거쳐 `add-domain`으로 문서를 등록하는 워크플로우입니다.

---

## 1. 도메인 발굴(Identification) 기준

다음 질문에 **"그렇다"**고 답할 수 있는 영역을 도메인 후보로 판별합니다:

1. **식별 가능한 생명주기와 상태가 존재하는가?** (엔티티 존재 여부)
   - 예: 주문(Order), 체결(Execution), 계좌(Account), 알림(Notification), 종목 감시(WatchItem) 등
2. **독립적인 비즈니스 불변식(Invariants)과 유효성 검증 규칙이 존재하는가?**
   - 예: 증거금 계산, 호가 단위 검증, 손익률 산출, 일일 한도 체크 등
3. **독자적인 원천 데이터(Source Data) 또는 외부 연동 API가 존재하는가?**
   - 예: KIS 실시간 웹소켓 체결통보, Supabase 사용자 설정/포트폴리오 테이블 등
4. **특정 화면에 종속되지 않고 재사용되거나 독립적인 상태(Zustand/React Query)를 갖는가?**
5. **기존 `docs/domain/`에 명세된 도메인들과 경계(Boundary)가 뚜렷하게 구분되는가?**

---

## 2. 워크플로우 실행 절차

### 단계 1: 프로젝트 현황 탐색 및 코드 스캔
1. **코드 디렉토리 스캔**:
   - `core/`: 핵심 알고리즘, 순수 비즈니스 로직, 상태 기계
   - `features/`: 비즈니스 로직, 유스케이스, 기능 모듈
   - `lib/`: 공용 유틸리티, API 클라이언트, 설정 매니저
   - `app/`: 라우팅 화면 구조 (Expo Router)
   - `supabase/`: DB 스키마 및 마이그레이션 정의
2. **기존 도메인 지도 확인**:
   - `docs/domain/README.md`를 조회하여 이미 등록된 도메인(모델, 추세, 기울기, 그리드, 매매, 오토파일럿, 순위 등)과 중복 여부 확인

### 단계 2: 도메인 후보 도출 및 DDD 적합성 평가
발굴된 후보에 대해 다음 요소를 정리합니다:
- **도메인 후보명**: (예: `계좌(account)`, `실시간시세(ticker-stream)`, `알림(notification)`)
- **주요 구성 요소**:
  - 엔티티(Entity)
  - 값 객체(Value Object)
  - 애그리게잇(Aggregate)
  - 도메인 서비스(Domain Service)
- **책임과 불변식**:
  - 자기 완결성 및 상태 보호 규칙
- **관련 코드 위치**:
  - 소스 파일 및 함수, 스토어 위치

### 단계 3: 사용자 보고 및 선택/승인
사용자에게 분석된 후보 목록과 추천 이유를 제시합니다:
```markdown
### 🔍 발굴된 도메인 후보 목록
1. [후보 1 이름]: 설명 및 발굴 근거
2. [후보 2 이름]: 설명 및 발굴 근거

-> 어떤 도메인을 `add-domain`으로 등록하시겠습니까?
```

### 단계 4: `add-domain` 워크플로우 연계 실행
사용자가 승인하거나 선택한 도메인에 대해 `add-domain` 워크플로우를 즉시 트리거하여 `docs/domain/{도메인명}/` 문서 세트를 작성합니다.
