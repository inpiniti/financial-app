# 매수 미체결 자동 취소 → 감시 복귀 (매수 한정, 기본 끔) — 2026-08-06

## 배경

매도 씹힘은 리프라이스로 풀었는데(2026-08-04) 매수도 안 붙는 경우가 생긴다. 매수는 매도와 반대로 **기회가 지나갔으면 포기**가 맞으므로, N초 안에 안 붙으면 취소하고 다시 변곡점을 기다린다.

### ⚠ 과거 실계좌 사고로 삭제됐던 기능의 재도입이다

체결확인 API가 거절당하는 상태에서 **매수는 실제 체결됐는데** 앱이 "오류 = 미체결"로 오판 → 자동 취소 → 취소도 실패했는데 무시 → "취소했으니 미체결"로 단정하고 감시 복귀 → 재매수 반복 → **중복 매수 3건 + 매도 미실행**. 결정타는 "취소 거절인데 원주문은 미체결로 잔존"(원인: ODNO 앞자리 0 잘림)이었다.

**본질은 "취소가 실패할 수 있는데 결과를 확인하지 않고 되돌린 것"**이다. 그래서 `BUYING → WATCH_BUY` 전이 자체가 코드에서 삭제돼 있었다.

## 되돌리는 경로에 증거 3겹

| 겹 | 요구 증거 | 없으면 |
|---|---|---|
| ① 요청 게이트 | odno 확보 + `cancelState === 'none'` + **관찰 체결량 0** | 취소를 걸지 않음(BUYING 유지) |
| ② 확정 게이트 | `cancelState === 'confirmed'` | 되돌리지 않음(= 기존 무한 대기) |
| ③ **사후 검증 폴** | 취소 확정 **후** 체결내역 재조회로 `filledQty === 0` 재확인 | `partialQty = undefined` → 되돌리지 않음 |

③이 핵심 신규 장치다. 어댑터는 `confirmed`가 되면 그 주문을 관찰에서 영구 제외하므로, **취소 확정과 거의 동시에 들어온 부분체결**을 영영 못 본 채 0주로 단정하게 된다 — 유령 포지션의 유일한 잔여 구멍이었다.

**fail-closed**: 애매하면 되돌리지 않고 BUYING에 머문다(= 검증된 무한 대기). 되돌리지 못한 채 부분체결이 드러나면 FAULT로 사람을 부른다.

## 사용자 확정 정책

1. 매수만. 매도는 불변(무한 대기 + 매수1호가 추종 정정).
2. **부분체결이면 취소하지 않고 기다린다** — 0주일 때만 취소.
3. **연속 3회 취소 시 60초 쿨다운**, 체결 성공 시 카운터 리셋.
4. **설정 기본 0(끔)** — 옵트인. 사고 재도입이라 사용자가 켰다는 인지가 있어야 한다.

## 설계 판단

**`stop()` 재활용 금지 · core 전용 메서드**: `stop()`은 DONE으로 가므로 러너가 `start()`를 다시 불러야 하는데, 그러면 detector가 리셋될 수 있고 타이머를 껐다 켜는 왕복이 생긴다. `abandonBuy()`가 **DONE을 스치지 않고** WATCH_BUY로 직행하므로 타이머·리샘플 버퍼·`prevSlope`가 전부 보존되고, 그 덕에 재매수에 최소 2~3청크의 구조적 간격이 유지된다(`crossedUp` 재성립에 실제 기울기 부호 반전이 필요).

**새 타이머를 만들지 않았다**: e2e 하네스가 인스턴스당 타이머 2개를 가정해 홀수 인덱스만 발화시킨다(`advanceAndReprice`의 stride 2). 기존 1초 리프라이스 틱을 상태별로 분기해 겸용했다 — 등록 순서·개수가 불변이라 테스트 가정이 전부 살아있다.

**취소 거절 유예**: 2~3초 자동 취소는 "취소 요청 중 체결" 레이스가 잦다. 즉시 FAULT면 오탐이 폭증하므로 abandon 사유만 3폴(≈6초) 유예한다. **Stop 사유는 유예 없이 즉시 FAULT**(기존 동작 불변) — `cancel`의 기본 사유를 `'stop'`으로 둔 이유다.

**자동관리는 `teardownActive()` 경유 필수**: 핀(`pin`)이 `commitBuy`에서 걸리고 `settle()`에서만 풀린다. 취소 경로가 이를 안 거치면 워치리스트가 영구 오염된다. 또 `reselect()`는 `watchedTickers=[]`에서 시작하면 히스테리시스를 안 타고 상위 3종을 채워 **방금 취소한 종목이 1순위로 즉시 재감시**되므로, 후보 필터(`!inAbandonCooldown(t)`)가 유일한 실효 장치다.

## 검증

vitest **408개 통과**. 기존 "취소 0회" 회귀 6개(core 2 · 인스턴스 2 · e2e 2)가 **무수정 통과** — 설정 기본 0 + core 무시계 + `cancel` 기본 사유 `'stop'` + 타이머 개수 불변 덕분이다.

사고 재현 테스트: 취소 확정이어도 **부분체결이면 복귀 안 함** / `partialQty` **undefined면 복귀 안 함**(모름을 0으로 단정 금지) / **취소 거절이면 복귀 안 함**(재취소도 0회) / 포기 대기 중 늦은 체결은 HOLDING(체결 우선) / Stop이 abandon을 이김 / **SELLING에서 `abandonBuy()`는 무동작**(매도 취소 금지 불변식) / 부분체결이면 취소를 안 걺 / 복귀해도 타이머 생존 / 자동 취소 경로가 `stop()`을 안 부름(FAULT 임의 해제 방지).

## 남은 일

- **실기기 검증**: 설정을 2~3초로 켜고 소액으로 돌려 (a) 취소가 실제로 확정되는지 (b) 취소 거절 빈도 (c) 쿨다운이 걸리는지 관찰.
- `fireCancel`이 원 주문수량으로 취소를 건다(`orderPortAdapter.ts`) — 부분체결이면 KIS가 거절할 소지가 있으나, 이번 설계는 부분체결 시 취소를 아예 안 걸어 우회한다. 잔량 기준으로 고치는 건 매도 Stop 경로까지 영향이 가므로 별건.
- 자동관리 `settle()`이 `record === null`이면 이벤트가 없다(진단 사각지대) — 이번 경로는 `abandonActive()`가 자기 이벤트를 내므로 무관하지만, 별도로 닫을 만하다.
