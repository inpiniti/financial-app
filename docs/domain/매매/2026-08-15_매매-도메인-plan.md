# 매매 (Execution) — 주문 실행 도메인 설계 (plan)

> 작성일 2026-08-15 · 분류: **도메인 문서** (2026-08-15 구현 완료)
> 선행: `docs/domain/변곡점/2026-08-15_변곡점-그리드-조합-plan.md`(판단 쪽 — "매수를 한다"까지만 정의하고 실행은 이 문서로 분리)
> 코드: `core/execution/index.ts`(Execution — 순수 상태기계), `features/scalper/executionPort.ts`(ScalperBroker 글루), 구동은 `features/scalper/autopilot.ts`(빠른 틱 1초=onPrice, 폴 2초=poll)

## 1. 역할 — 판단은 변곡점, 실행은 매매

- **변곡점(+그리드 조건)**이 "지금 사라 / 지금 팔아라"를 **판단**한다.
- **매매**는 그 지시를 받아 **책임지고 체결까지 수행**한다. 무엇을 왜 사는지는 모른다 — 방향(매수/매도)·수량만 받는다.
- 매매의 결과는 둘 중 하나다: **체결 완료** 또는 **취소 후 반납**(변곡점 판단 대기로 복귀).

```
변곡점 판단 ──"매수 n주" / "전량 매도"──▶ 매매 ──▶ 체결 완료 (끝)
                                          └──▶ 취소 (판단 쪽에 반납, 다음 변곡점 대기)
```

## 2. 실행 규칙 — 현재가 추격 지정가

1. **현재가로 지정가 주문**을 넣는다 (매수든 매도든 동일).
2. **체결되면 그대로 끝.**
3. 미체결 상태에서 **실시간 체결가(현재가)가 바뀌면** → 기존 주문 **취소** 후 **새 현재가로 재주문** (추격).
4. 추격 중 **취소선**에 닿으면 → 주문 취소하고 매매 종료. **변곡점의 다음 판단을 다시 기다린다.**

### 2-1. 취소선 — 평단가와의 차이가 진입 문턱 미만으로 좁아지면 포기

취소선은 판단 쪽의 진입 문턱을 그대로 재사용한다 (2026-08-15 확정):

| 방향 | 진입 조건 (평단 대비) | 추격 중 취소선 |
|---|---|---|
| **매수** (물타기) | -3% 이하 | 낙폭이 **3% 미만**으로 좁아지면 취소 |
| **매도** (익절) | +2% 이상 | 이득이 **+2% 미만**으로 좁아지면 취소 |

- 의미: 추격하는 동안 가격이 반대로 움직여 **진입 근거 자체가 사라지면**, 억지로 체결하지 않고 포기한다. 매수 추격 중 가격이 올라 낙폭 3%가 깨지면 "충분히 싼 물타기"가 아니게 된 것이고, 매도 추격 중 가격이 내려 +2%가 깨지면 "수익 문턱을 넘긴 청산"이 아니게 된 것이다.
- 취소 후에는 매매가 임의로 재시도하지 않는다. **재시도 여부도 판단(변곡점)의 몫**이다.

### 2-2. 상태기계

```
IDLE ──지시 수신──▶ ORDERED(현재가 지정가)
ORDERED ──체결──▶ DONE (판단 쪽에 체결 보고)
ORDERED ──현재가 변동──▶ 취소 → 재주문 (ORDERED 유지, 새 가격)
ORDERED ──취소선 도달──▶ CANCELLED (판단 쪽에 반납, 변곡점 대기)
```

## 3. 설계 원칙

1. **매매는 판단하지 않는다** — 문턱 %값(3%/2%)은 판단 쪽 설정에서 주입받는다. 매매가 자체 판단 로직을 가지는 순간 책임 분리가 깨진다.
2. **시장가 아님** — 항상 현재가 **지정가** + 추격. 슬리피지를 주문 갱신으로 통제한다.
3. **주문은 항상 1개** — 재주문은 반드시 "기존 취소 확인 → 신규 제출" 순서. 취소 실패·지연 상태에서 이중 주문이 나가면 안 된다.
4. **끝맺음 보고** — DONE(체결가·수량)이든 CANCELLED든 판단 쪽에 결과를 반드시 돌려준다. 판단은 이 보고를 받아야 다음 변곡점 감시로 넘어간다.

## 4. 열린 문제의 확정 (2026-08-15 구현)

1. **재주문 빈도 제한** — 추격은 빠른 틱(1초)에서만 구동하고, Execution 내부에 재정정 최소 간격 스로틀(기본 1초, `minReorderIntervalMs`)을 둔다. 같은 가격이면 정정하지 않는다.
2. **부분 체결** — **잔량만 추격**한다. 취소선 도달 시 잔량만 취소하고 체결분을 보고(CANCELLED + filledQty)하면, 판단 쪽이 잔고 재조회로 평단·수량을 갱신한다.
3. **취소 실패/미확인** — 취소·정정 거절은 "이미 체결"이 가장 흔한 원인이라 **재발사하지 않고**(과거 사고의 증폭 요인) 폴이 체결을 확정하길 기다린다. 한도(기본 3폴)까지 체결도 안 보이면 그 종목만 격리 FAULT(사람 호출).

## 5. 구현 메모 (2026-08-15)

- **추격은 취소→재발주가 아니라 정정(amend)** — KIS 정정은 새 ODNO를 채번하는 원자 교체라 무주문 공백·이중 주문 레이스가 없고 REST 1회로 끝난다(§3-3 "주문은 항상 1개"의 구현). 옛 다리의 부분 체결은 적립(bank)해 가중평균으로 합산한다.
- **추론 체결 방어** — "미체결 목록 부재→전량체결" 추론(체결가 미실측)으로 DONE이 되면 `priceConfirmed=false`를 보고하고, 매도 정산 쪽(autopilot)이 잔고로 재검증한다 — 세션 일괄 취소를 체결로 오판해 없는 매도를 정산하는 사고 방지.
- **release(외부 종료)** — 사용자 Stop 경로 전용. 잔량을 최선껏 취소하고 CANCELLED로 마감하며, 거절돼도 재시도 없이 종료한다(잔여 주문 안내는 호출부 몫).
- 테스트: `core/execution/index.test.ts`(추격·부분 체결·취소선·거절 구제·장애 한도 전 분기).

## 6. 사고와 수정 (2026-08-18) — 정정 거절을 재발사하다 FAULT

**증상**: WFF 매수($7.61)가 급락으로 전량 체결됐는데 "정정 3회 연속 거절 — APBK0124 매매가능한 수량이 없습니다"로 그리드 관리가 멈춤. APBK0124는 정정취소 API에서 **원주문 잔량 없음**(=이미 체결) 거절이다.

**원인**: §4-3은 "정정 거절은 재발사하지 않고 폴 확정 대기(한도 3폴)"인데, 구현이 정정 쪽만 달랐다 — 동결 없이 스로틀(1초)마다 재정정을 쏘며 **시도 3회**를 세서 약 2초 만에 FAULT. 폴(2초 주기 + nccs 반영 지연)이 체결을 확정할 시간이 없었고, 정정 REST 왕복 중이면 `busy`로 폴이 조회를 거르기까지 했다.

**수정** (`core/execution` + 브로커 `listed` 실측 신호):

- 정정 거절 → **재정정 동결**(amendAmbiguous) → 폴의 **수량 실측**이 판정한다:
  - 미체결 목록 부재 → 전량체결 확정 → **DONE** (체결가 미실측이면 `priceConfirmed=false` → 호출부 잔고 재검증 — 이번 사고의 정상 경로).
  - 목록에 **잔량과 함께 생존**(BrokerFill.listed=true) → 거절은 일시 장애 — 동결 해제, 추격 재개.
  - 한도 폴(기본 3)까지 둘 다 확인 안 되면 FAULT(모호 — 사람 호출).
- `amendFailLimit`(3)의 의미 변경: "1초 간격 시도 3회"가 아니라 **생존 실측 후 재개했는데 또 거절**이 3라운드 — 진짜 API 장애만 남는다.
- 회귀 테스트: `core/execution/index.test.ts` "정정 거절(이미 체결·APBK0124 시나리오) → 폴이 체결을 확정하면 FAULT 없이 DONE".
