## 1. 왜 — 고정 금액의 한계

현재 진입 수량은 **설정 고정값**(`startAmountUsd ÷ 현재가`)이다. 추세 전략이 기대대로 "수익은 크고, 손실은 작고, 대신 자주 발생"하는 분포를 실제로 만들어낸다면, 고정 금액은 두 방향으로 비효율이다:

- 잘 벌리는 구간에서도 자본이 늘어난 만큼 베팅을 키우지 않아 **복리 성장률을 못 먹는다**.
- 반대로 성적이 나빠지는 구간에서 베팅을 줄이지 않아 **연속 손실이 자본을 정직하게 깎는다**.

켈리 공식은 "이 손익 분포에서 자본의 장기 성장률을 최대로 하는 베팅 비율"을 준다. 성적이 좋으면 비율이 커지고 나빠지면 자동으로 작아지므로, **진입 빈도보다 청산 위험 최소화** 원칙과 방향이 같다 — 단, 원형 그대로는 변동성이 너무 커서 조회에서도 **반켈리**를 함께 본다(§3).

이 도메인이 최종적으로 답할 질문은 "얼마를 넣을지"지만, **현 단계의 범위는 §4 기록과 §5 조회다.** 켈리 비율은 화면에 보여주는 척도일 뿐 진입금액·PAUSED·어떤 매매 판단에도 들어가지 않는다(§6). 사이징 적용(§7-후반)은 기록이 쌓인 뒤 다시 결정한다.

## 2. 켈리 공식 — 개념

### 2-1. 이산형(승/패 두 결과)

```
f* = p − (1 − p) / b
   p = 승률 (이익 거래 수 ÷ 전체)
   b = 손익비 = 평균 이익(이익 거래의 평균 수익률) ÷ 평균 손실(손실 거래의 평균 손실률, 양수)
```

- 예: 승률 40%, 평균 이익 +6%, 평균 손실 −1.5% → b=4 → f* = 0.4 − 0.6/4 = **0.25**(자본의 25%).
- 예: 승률 30%, b=2 → f* = 0.3 − 0.7/2 = **−0.05** → 음수 = 베팅하지 말라. 이 값이 나오면 켈리 사이징이 아니라 **전략 자체를 멈추는** 신호다.

### 2-2. 연속형(수익률 분포 사용)

```
f* ≈ μ / σ²      μ = 거래당 평균 수익률, σ² = 거래당 수익률 분산
```

거래마다 손익 크기가 제각각인 추세 전략에는 이쪽이 자연스럽다. 두 식은 같은 데이터에서 다르게 나올 수 있으므로 **둘 다 계산해 작은 쪽**을 쓴다(보수).

### 2-3. 수익률의 정의(정본)

```
거래 수익률 r = 순손익 pnl ÷ 진입금액 (entry_price × qty)
```

수수료·슬리피지가 포함된 **순손익**(`TradeRecord.pnl`) 기준. 총손익(grossPnl)로 계산하면 비율이 부풀어 실제보다 크게 베팅한다.

## 3. 변형 켈리 — 조회에서 보여주는 값

원형 켈리는 추정 오차에 극도로 민감하다(승률·손익비가 조금만 틀려도 최적점을 크게 지나쳐 파산 확률이 급증). 그래서 조회 화면은 원형과 함께 **반켈리(×0.5)** 를 나란히 보여준다(2026-08-18 확정 — 반켈리는 성장률의 약 3/4를 유지하면서 변동성은 크게 줄어든다는 것이 통상 결론).

```
입력:  최근 n건 수익률 (n = 조회 시 입력한 수량, 미입력이면 저장된 전체 기록)
       + 전략 태그 필터(strategy='trend' 등)
계산:  f_disc = p − (1−p)/b,   f_cont = μ/σ²
       f_raw  = min(f_disc, f_cont)          — 보수 선택
       f_half = f_raw × 0.5                  — 반켈리
표시:  n · 승률 p · 평균 이익/손실 · 손익비 b · μ · σ · f_disc · f_cont · f_raw · f_half
       f_raw ≤ 0 이면 "음수 엣지(이 표본으론 베팅 근거 없음)"라고 **표시만** 한다 — 어떤 동작도 하지 않는다.
       n이 작으면(초안 30 미만) "표본 부족" 뱃지 — 역시 표시만.
```

- **창 크기는 조회 파라미터다.** 설정값이 아니라 조회 화면에서 수량을 입력하면 최근 그만큼만, 비우면 전체. 그래서 "최근 20건 vs 전체"를 그 자리에서 비교할 수 있다.
- 상하한(f_min·f_max)·동시 그리드 분할·진입금액 환산은 **사이징 적용 단계**의 것이라 지금은 계산하지 않는다(§7-후반에 옮김).

## 4. 거래 결과 기록 — Supabase

### 4-1. 지금 상태와 문제

거래 기록은 `features/scalper/tradeStore.ts`가 **AsyncStorage(기기 로컬)** 에 `StoredTrade[]`로 쌓는다. 앱 삭제·기기 교체로 유실되고, 집계·필터 쿼리를 앱 안에서 돌려야 하며, 시뮬레이션·다른 기기에서 볼 수 없다. 켈리 계산은 **수십~수백 건의 이력**이 있어야 하므로 유실되지 않는 저장소가 필요하다.

→ Supabase 테이블 `trade_results`에 **정산 시점마다 1행 insert**. 로컬 tradeStore는 그대로 두고(화면·오프라인 폴백) Supabase는 **추가 기록처**다 — 기록 실패는 매매를 멈추지 않는다(fail-open, surge_events와 같은 원칙).

### 4-2. 스키마 — `supabase/migrations/0006_trade_results.sql` (초안)

```sql
-- 0006_trade_results.sql
-- 거래 결과 기록 (docs/domain/켈리). 켈리 비율 도출·성과 분석용. 매매 판단·주문 중계는 하지 않는다.

create table if not exists trade_results (
  id                uuid primary key default gen_random_uuid(),

  -- 누구·어떤 전략
  account_no        text not null,             -- 계좌 식별(approved_users와 같은 값) — 기기가 바뀌어도 이력이 이어진다
  strategy          text not null,             -- 'trend' | 'inflection' | 'ladder' | 'grid' — 진입·청산 규칙 태그. 켈리는 전략별로 따로 센다
  exit_reason       text not null,             -- TradeRecord.exitReason (SELL_SIGNAL·STOP 등)

  -- 종목
  ticker            text not null,
  market            text,                      -- NAS/NYS/AMS
  name              text,

  -- 체결
  qty               numeric not null,
  entry_price       numeric not null,
  entry_at          timestamptz not null,
  exit_price        numeric not null,
  exit_at           timestamptz not null,

  -- 손익 (USD). pnl = 순손익(수수료 차감) — 켈리 수익률의 정본
  gross_pnl         numeric not null,
  fees              numeric not null default 0,
  pnl               numeric not null,

  -- 사이징 맥락 — 그때 얼마를 어떤 근거로 넣었는지. 나중에 "켈리였다면?"을 되돌려 보는 데 필요
  entry_amount_usd  numeric generated always as (entry_price * qty) stored,
  return_pct        numeric generated always as
    (case when entry_price * qty > 0 then pnl / (entry_price * qty) * 100 end) stored,
  equity_usd        numeric,                   -- 기록(정산) 시점 계좌 총평가(USD 근사 = 원화 총자산 ÷ 기준환율) — 비율 역산용. 조회 실패면 null
  sizing_mode       text not null default 'fixed' check (sizing_mode in ('fixed', 'kelly')),
  kelly_fraction    numeric,                   -- 켈리 모드였다면 적용한 f (분수·상하한 반영 후). fixed면 null

  -- 진입 시점 신호 스냅샷 (추세: 4선 값·상승 플래그·종가>60선 등) — 사후 분석용, 스키마 자유
  entry_snapshot    jsonb,
  exit_snapshot     jsonb,

  app_version       text,
  created_at        timestamptz not null default now()
);

create index if not exists trade_results_account_strategy_exit_idx
  on trade_results (account_no, strategy, exit_at desc);
```

### 4-4. 기록 시점·배선 (2026-08-18 구현)

- 트리거: `AutoPilotManager`의 `onTrade`(로컬 `appendTradeRecord` 직후) — deps.`recordTradeResult`를 **await 없이** 부른다. provider가 `TradeResultRecorder.record`로 구현하고, 실패(false)면 throw → 매니저가 이벤트 1건("거래 기록 업로드 실패 · …")을 남기고 끝. 매매·로컬 기록 무영향.
- `strategy`는 매니저 `strategyTag()`가 스위치·주입 조합에서 읽는다: trend → inflection → ladder → grid 순. `equity_usd`는 **정산 시점** 잔고 조회(`inquireOverseasBalance`) 원화 총자산 ÷ 기준환율의 USD 근사(진입 시점이 아니라 정산 시점 — 진입 시 잔고를 들고 다니지 않기 위한 단순화). 실패면 null.
- 미업로드 행 재전송: 실패 행은 AsyncStorage `tradeResults.pending`(상한 500, 오래된 것부터 버림)에 보관하고 **부팅(매니저 빌드) 시** `flushPending`으로 직렬 재전송. 도중 실패하면 거기서 멈추고 나머지는 다음 부팅에. 중복 방지는 `(account_no, ticker, exit_at)` 유니크 인덱스 — 23505 위반은 "이미 올라감"으로 성공 처리.

## 5. 비율 도출 — 어디서, 어떻게

### 5-1. 계산 위치: 앱 안 순수 함수 (`core/kelly`)

Supabase에서 **최근 n건(또는 전체)을 조회**해 오고, 계산은 앱 안 순수 TS(`core/kelly/index.ts`)가 한다. DB view/RPC로 집계하는 대안도 있지만:

- 계산이 단순(평균·분산·클램프)해 클라이언트로 충분하고,
- **순수 함수라야 배열 재생 단위 테스트**가 된다(돈이 걸린 로직 — 변곡점·매매·추세 도메인과 같은 원칙),
- 파라미터(k·상하한·창)를 바꿀 때 마이그레이션이 필요 없다.

```ts
// core/kelly (설계 초안) — 순수 통계. 매매·설정을 모른다.
interface KellyResult {
  n: number;
  winRate: number | null;        // n=0이면 null
  avgWin: number | null;         // 이익 거래 평균 수익률(소수)
  avgLoss: number | null;        // 손실 거래 평균 손실률(양수, 소수)
  payoff: number | null;         // b = avgWin / avgLoss
  mean: number | null;           // μ
  variance: number | null;       // σ²
  discrete: number | null;       // f_disc
  continuous: number | null;     // f_cont
  raw: number | null;            // min(discrete, continuous)
  half: number | null;           // raw × 0.5
  flags: { insufficientSamples: boolean; negativeEdge: boolean };
}
computeKelly(returns: readonly number[] /* 소수, 순서 무관 */, opts?: { minSamples?: number }): KellyResult
```

- 조회 쿼리(`fetchTradeReturns`): `trade_results` where `account_no = ? and strategy = ?` order by `exit_at desc` [limit n] → `return_pct / 100` 배열(null은 버림).
- **조회 시점**: 사용자가 조회 화면을 열거나 수량을 바꿀 때만. 자동 재계산·캐시·매매 배선 없음.

### 5-2. 표시 (조회 전용 화면)

- 홈 손익 섹션 하단 "켈리 배율 (조회)" 섹션(`features/inquiry/KellySection.tsx`, 일별 손익 리스트의 footer): 전략 `SelectBox` + **최근 n건 입력**(비우면 전체) + 조회 버튼, 아래 `ListRow`로 표본 수·승률·평균 이익/손실·손익비·μ/σ·f_disc·f_cont·**켈리 f_raw**·**반켈리 f_half**. 표본 부족·음수 엣지는 값 옆 회색 뱃지. 전략을 바꾸면 즉시 재조회, 수량은 조회 버튼/엔터로.
- 설정 화면에는 아무것도 추가하지 않는다(매매와 무관하므로).

## 6. 원칙 (현 단계 — 기록·조회)

1. **매매와 완전 분리.** 켈리 값은 진입금액·PAUSED·신호·어떤 판단에도 들어가지 않는다. `core/kelly`는 `AutoPilot`·`AutoPilotManager`가 import하지 않는다(의존 방향으로 강제).
2. **음수 엣지·표본 부족은 표시일 뿐** — 멈추지 않는다, 이벤트도 내지 않는다.
3. 기록 실패는 매매를 멈추지 않는다(fail-open). 로컬 tradeStore가 정본이고 Supabase는 추가 기록처.
4. 전략 태그를 섞지 않는다 — 변곡점 시절 기록으로 추세의 f를 계산하면 안 된다. 조회는 항상 전략 필터를 건다.
5. **자본(`equity_usd`)은 기록 시점 잔고 조회값** — 나중에 "켈리였다면"을 되돌려 보는 데만 쓴다.
